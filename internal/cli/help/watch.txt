tkt watch keeps a repository's tickets moving, every ticket and not only the
ones you hand to tkt auto. Every [watch] interval (60s) it fetches, reads
every ticket with a fixed number of gh calls, and takes at most one step per
ticket, from the same rules as tkt ls:

  - finish-ticket ended with Status: DONE after the merge, or the pull
    request was closed without merging and no agent works on it: it runs
    tkt done, unless [watch] done_after_merge = false; after a close, the
    tracker is yours to move;
  - the base moved at a moment a sync is due (a conflict, the bot's
    STALE_BASE, BLOCKED_FOR_SYNC behind the base): it merges a clean base
    itself, as tkt sync does, with no agent, and runs resolve on a conflict;
  - the checks fail at the head: it runs ci in a fresh session, in a split
    beside the ticket's agent, once per head; a sync that failed another
    way gets sync-fix there;
  - a ticket marked for auto whose tkt auto loop is gone, as after a
    reboot: it starts the loop again, in the mode it had;
  - a merge order from tkt merge holds at the head, its checks passed and
    review-pr's READY_FOR_HUMAN is at the head: it sends finish-ticket the
    merge line in a fresh session, for one ticket at a time. A base that
    moved gets a sync first, and the order holds across that clean merge.
    A head review-pr has not cleared, such as one a sync made or one only
    the review bot cleared, gets review-pr in a fresh session, unless
    workflow.md turns CI review on: then the bot's CLEAR is the review,
    and the order waits for it. A new head
    of any other kind, a failed human verification step, or another
    session taking the ticket over after the line went out drops the
    order, with a notification.

Everything else waits for you or for tkt auto: plans, the other reviews,
findings, human verification and the word to merge. It leaves alone a ticket on hold (tkt
hold), one a tkt auto loop drives, one another tkt command works on, one
whose agent works or asks a question, and one whose worktree directory is
gone. It replaces an agent with a fresh session only after the agent sat
idle for five minutes, since a person may still use that session, and it
waits while the forge still shows an older head than the branch has. A step
it would repeat on the same head, or a fix run past [auto] max_rounds, waits
for you instead: tkt ls shows the ticket as needs_you, with watch.paused
saying why, and herdr notifies once.

Its agent runs take the [auto] max_parallel slots tkt auto uses. It records
each step in the history, and shows a herdr notification for each agent run,
failure and removal; a clean sync stays quiet. A sync that fails, such as
while the network is down, is tried again at the next pass, with one
notification for each head and reason.

It also starts the repository's chores, the agent runs its
.tkt/tkt.local.toml schedules, when their slot comes (tkt help chores): once per slot, however
many slots passed while no watch ran, and never while the chore's last run
is still open. A chore's run is a row like a ticket's: watch syncs its base
when a sync is due, fixes its checks, and removes the run once you merged
its pull request, or once its agent ended with nothing to change.

The [status.NAME] tables in config.toml and the .tkt files name status pages, such as GitHub's
(tkt help config). tkt watch reads them every five minutes. While one
reports a problem with a component that counts, it starts no agent: no ci,
resolve or review run, no merge line and no chore run, since each would only
spend a round on a service that is down. Syncs and removals, which need no
agent, go on, and tkt auto loops wait the same way (tkt help auto). It notifies when an incident starts and when it ends, and tkt
ls and the tkt agent's board show it while it lasts. A page it cannot read
keeps what it said last for fifteen minutes after its last answer, then
holds nothing back.

One tkt watch runs per repository. Every tkt command in a herdr pane starts
it when none runs, in a session of its own, so it outlives the command and the
pane; it writes its lines to watch.log in the repository's git directory,
under tkt/. It waits a minute between two starts, so a watch that exits at
once is not started again by every command. [watch] autostart = false, or
TKT_WATCH=off, turns that off. tkt ls --json says whether it runs, in
watch.running, and watch.error says why its last pass failed. tkt watch
--stop stops it, after the step it is taking; a second SIGTERM stops it at
once. When tkt update replaces tkt, the watch stops by itself, and the next
tkt command starts one that runs the new tkt.

Outside a herdr pane it finds the workspace whose panes work in the
repository. When none has a pane there, it opens one before its first step,
since every step works in herdr. While herdr is down it waits.

--install keeps it running while no terminal is open: it writes systemd user
units, or launchd agents on macOS, for herdr's server and for this
repository's tkt watch, with this shell's PATH, since the agents in herdr's
panes inherit herdr's. It asks before loginctl enable-linger, which keeps
the units running past your last session and starts them at boot; --yes
answers yes, and without a terminal the answer is no. Without linger,
systemd stops the units when your last session ends, so herdr's unit stays
off, since it would take every agent with it, and tkt watch runs from login
to logout. With linger, herdr's unit goes on, and starts unless herdr
already runs. tkt commands then start the unit rather than a watch of their
own, and --stop stops the unit, which signals tkt watch alone, so it
finishes the step it took. --uninstall removes this repository's unit;
herdr's stays. tkt doctor checks that they run and that their PATH finds the
tools and harnesses.

--once takes one pass and exits; with --dry-run it says what each ticket would
get, and changes nothing. --install and --uninstall take --dry-run too.
