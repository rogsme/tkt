tkt sync brings the ticket's branch up to date with its base, without an
agent whenever it can. It fetches, then merges the base in memory with git
merge-tree, which touches neither the worktree nor the branch:

  - When the merge is clean, tkt makes the merge commit itself and pushes it,
    in seconds. CI and the review bot then run on the new head.
  - When it conflicts, a fresh session runs the resolve stage, in a split
    beside the ticket's agent: it merges the base, resolves each conflict
    from what both sides meant, changes nothing else, and pushes once.
    Review findings stay for address. --no-agent stops at the conflict
    instead, with exit 4.
  - When the sync fails another way after its fetch, as when a pre-push
    hook refuses the push, a fresh session runs the sync-fix stage in a
    split: its line says why the sync failed and names the log of git's
    output, and it fixes the cause and pushes once. --no-agent stops with
    the error instead.
  - When the branch already contains the base, it does nothing.

It never rebases and never force-pushes. A merge commit tkt made counts as
clean for the review brief: its tree equals what git merge-tree gives for
its two parents, which review-pr checks for itself.

tkt sync refuses while an agent works in the worktree, while the worktree has
uncommitted changes to tracked files (an untracked file does not count),
before the branch is on the remote, and when the branch has commits the
remote lacks, since it pushes only its own merge. When someone pushed to the
branch since the worktree last moved, it fast-forwards first. It pushes the
merge commit it checked, and when the push fails, or you press Ctrl-C, it
takes its merge back off the branch, unless a commit came on top of it
meanwhile: then it leaves the branch alone and says how to drop the merge.

The merge and the push run the repository's hooks, which may run its whole
test suite, so they take a turn first. At most [sync] pushes syncs (2) on the
machine merge and push at once, whatever their repository, and each starts
only while [sync] min_free of memory (20%) is free. tkt sync waits for its
turn and says once what it waits for, up to 30 minutes; tkt watch and tkt
auto never wait, and take the sync again at their next look. The fetch and
git merge-tree never wait. On Linux, the push and its hooks are the first
thing the kernel stops when memory runs out, before the agents.

A sync killed before it could push its merge or take it back, as when
memory ran out, leaves the merge at HEAD. The next sync drops a merge like
that when it can make it again exactly: a clean merge of the base onto the
branch's head on the remote, which nobody changed. It then merges the base
as it is now, and --json names the merge it dropped under dropped. Any other
commit the remote lacks stays, and the sync refuses as before.

Whenever a sync fails after its fetch, tkt keeps why. tkt ls --json shows the reason under the row's sync while the
head is the one it failed on, tkt history lists it, and a log in the
ticket's temporary directory holds everything git and its hooks printed. A
sync that works forgets it.

Sync at the moments a ticket needs it: the pull request conflicts, a review
cannot happen because the base moved (the bot's STALE_BASE, or review-pr's
BLOCKED_FOR_SYNC), or a merge is due and finish-ticket stopped with
BLOCKED_FOR_SYNC. tkt ls suggests it then, and tkt auto runs it. Syncing on
every move of the base costs a CI run and a review per ticket for nothing.
