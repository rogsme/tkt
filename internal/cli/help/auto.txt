tkt auto drives one ticket through the lifecycle and pauses where a person
decides. It reads the same facts as tkt ls, then:

  - starts the ticket when it has no worktree yet, on --as PRESET when given;
    with --auto-plan its start line says the run is unattended, so
    start-ticket skips the browser plan presentation and asks every open
    question with the harness's question tool;
  - waits while the agent works, or waits on its own background task such
    as a CI watcher;
  - approves the plan when start-ticket ends with AWAITING_APPROVAL, but only
    with --auto-plan; without it the loop pauses there for you;
  - waits for CI, then for the review bot in CI to review the new head;
  - merges a moved base itself when the merge is clean, as tkt sync does,
    with no agent and no fix round; on a conflict it runs resolve, which only
    merges and resolves (it runs git merge-tree on each look to tell the
    two apart);
  - runs address on findings, and ci when checks fail, each in a fresh
    session;
  - once the head is reviewed clean (the bot's CLEAR, or review-pr's
    READY_FOR_HUMAN; review-pr runs only in a repository with no review bot,
    [review] bot_wait = "0s", and never where workflow.md turns CI review
    on), runs verify where workflow.md turns agent
    verification on: verify-pr runs the human verification steps and posts
    what it saw. A step it reports failed gets an address run, which counts
    as a fix round, then a new review and a new verify;
  - ends with success when the head is reviewed clean and, with agent
    verification on, verify-pr passed every step or could not run some.

Without --yolo it never merges and never removes a worktree.

--yolo carries the ticket to the merge with nobody watching. It runs only
where workflow.md turns on autonomous runs, agent verification and plan
review, and refuses with autonomous_off naming the rows that are off. A
yolo run starts with the ticket: --yolo refuses a ticket that started
without it, since start-ticket posted no Autonomous run comment, which
finish-ticket merges on. It
approves the plan as --auto-plan does, and every line its agents get,
from the start line to the merge line, says "This run is autonomous", so
the skills decide what they would ask, record each decision as an
assumption, and stop at the hard stops workflow.md lists instead of asking
(tkt help lifecycle). A head only the review bot cleared gets review-pr
first, since finish-ticket merges on its verdict alone; then verify-pr
runs, and once its report passes every step the loop sends finish-ticket
the autonomous merge line with tkt merge --autonomous, one merge at a time
in the repository. It waits for finish-ticket after the merge: Status: DONE
ends it with merged, and tkt watch removes the ticket; a failure of the
checks on the base ends it with post_merge_failed and a notification, and
nothing else happens. Steps verify-pr could not run pause it (needs_you).
The ticket stays a yolo one when its loop starts again, and every line tkt
sends it says so, until tkt auto --stop hands it back to you, dropping
any merge order it left. A merge line you send yourself never says the run
is autonomous, so finish-ticket takes your word. tkt ls shows
auto.yolo, and yolo in the AUTO column while the loop drives it.

Where a person decides, the loop pauses instead of ending: when the agent
asks a question or ends with Status: BLOCKED (needs_you), when the plan waits
and --auto-plan is off (plan_awaits_approval), when no agent runs
(agent_missing), when the bot has not reviewed a head after [review] bot_wait
(bot_silent), after [auto] max_rounds fix runs since the plan's approval
(round_limit), when a step would repeat on the same head with nothing
changed (no_progress), when tkt sync cannot merge the base for now, such as
with uncommitted changes in the worktree (sync_failed: it tries again at each
look, and tkt ls says why in auto.note), and while the ticket is on hold
(hold, with no notification). It records the pause, which tkt ls shows as
auto.paused, notifies once with --notify, and goes on by itself when the
ticket moves, such as after you answer the agent in its tab or approve the
plan.

A loop ends only when the ticket is ready for you, merged, or closed
without merging, which tkt watch then removes (with --yolo, also when the
checks on the base fail after the merge), or with tkt auto --stop, which it
notices at its next look. Ctrl-C ends it with exit 5 and leaves the ticket
marked for auto, so tkt ls shows auto.wanted. While a loop drives the
ticket, its tab reads ACM-12 (claude, auto).

When tkt update replaces tkt, a loop restarts on the new tkt at its next
look, once its agent stops working: the same process runs the same command
again. It keeps the pause it notified you about, so it does not notify it
twice.

At most [auto] max_parallel tkt auto agents work at once in a repository. A
loop holds a slot while its agent works and gives it up while it waits for CI,
the bot or you. A ticket waiting for a slot shows as queued in tkt ls, even
before it has a worktree.

While a status page that the running tkt watch reads reports an incident
(tkt help watch), the loop sets no agent to work: it starts, approves and
runs nothing, and spends no round, until the incident ends. A sync needs no
agent and goes on. tkt ls shows incident in auto.waiting, and --once says it
waits for the incident. tkt run starts an agent anyway.

--once takes at most one step and exits 0, saying what it did, what it waits
for, or why it would stop or pause. With --dry-run it prints the step instead.
--notify shows a herdr notification when the loop pauses for you or ends.
